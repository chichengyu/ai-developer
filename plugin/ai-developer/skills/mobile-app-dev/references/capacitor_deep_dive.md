# Capacitor deep dive

Read this when Step 1.5 picks Capacitor (usually because a web app
already exists and a thin native shell is enough).

## When to use

- Existing PWA / responsive web app that needs store distribution.
- Team is web-first and does not want to rewrite in Flutter / RN.
- App can stay WebView-rendered without losing the core experience.

## When NOT to use

- Heavy animation, canvas, or 120 Hz ProMotion polish.
- Deep OS integration: widgets, HealthKit, CarPlay, Wear OS tiles.
- Apps where reviewers expect native look and feel.

## Project shape

```
my-app/
  www/                       web assets served by WebView
  capacitor.config.json      appId, appName, webDir
  package.json               @capacitor/core + cli
  ios/                       generated by `npx cap add ios`
  android/                   generated by `npx cap add android`
```

## Commands

```bash
npm install
npx cap add ios
npx cap add android
npx cap sync
npx cap open ios
npx cap open android
```

## Deep links and permissions

- Register URL schemes / App Links in the native projects after
  `cap sync`; do not edit the generated files before regenerating.
- `Camera`, `Geolocation`, and other plugins request native
  permissions; the usage strings live in the native Info.plist /
  AndroidManifest.xml, not the web app.

## Build

Use `scripts/build_capacitor.ps1` or:

```bash
# iOS
xcodebuild -workspace ios/App/App.xcworkspace \
  -scheme App -configuration Release \
  -destination "generic/platform=iOS" archive

# Android
cd android && ./gradlew :app:assembleRelease
```

## Common review pitfalls

- Shipping a WebView that only mirrors a public website can be
  rejected as a "thin wrapper".
- Leaving `NSAllowsArbitraryLoads` enabled is a red flag.
- Not testing offline behavior; Capacitor apps inherit the web app's
  offline story.
